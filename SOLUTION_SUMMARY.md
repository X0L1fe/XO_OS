# Решение проблем с регистрацией, подтверждением email и входом в систему

## Выполненные изменения бэкенда

### 1. Исправлена ошибка сравнения дат (`can't compare offset-naive and offset-aware datetimes`)
- **Файл:** `app/auth/service.py`
- **Функции:** `verify_email`, `verify_and_reset_password`, `confirm_email_change`
- **Что сделано:** Добавлена обработка случая, когда время из БД приходит без информации о часовом поясе (SQLite возвращает naive datetime). Теперь перед сравнением с `datetime.now(timezone.utc)` проверяется наличие `tzinfo`, и если его нет, предполагается, что время находится в UTC (`expires.replace(tzinfo=timezone.utc)`).
- **Результат:** Ошибка TypeError при проверке срока токена больше не возникает.

### 2. Изменён метод эндпоинта подтверждения email на GET с параметром в query string
- **Файл:** `app/main.py`
- **Эндпоинт:** `/api/auth/verify-email`
- **Изменение:** Возвращено к `@app.get("/api/auth/verify-email")` и `token: str = Query(...)`.
- **Почему:** Ссылка в письме подтверждения формируется как `{{FRONTEND_URL}}/verify-email?token={{VERIFICATION_TOKEN}}` (см. шаблон `verification_email.html`). Поэтому эндпоинт должен принимать токен через query parameter, а не через тело POST-запроса.
- **Результат:** Переход по ссылке из письма теперь корректно обрабатывается сервером.

### 3. Устранена причина 500‑ошибки при регистрации
- **Файл:** `app/main.py`
- **Эндпоинт:** `/api/auth/register`
- **Изменение:** Вместо использования Pydantic модели `UserResponse.model_validate(db_user).model_dump()` (которая могла вызывать ошибки сериализации) теперь формируется ответ вручную:
  ```python
  user_data = {
      "id": db_user.id,
      "name": db_user.name,
      "email": db_user.email,
      "onboarding_completed": bool(db_user.onboarding_completed),
  }
  ```
- **Результат:** Регистрация возвращает 200 OK при successful creation and email sending, а не 500 Internal Server Error.

### 4. Переименован импорт функции проверки email для избежания конфликта имён
- **Файл:** `app/main.py`
- **Изменение:** `from app.auth.service import (... verify_email as verify_email_service, ...)`.
- **Результат:** Избегает путаницы между локальной функцией `verify_email` (эндпоинт) и импортированной функцией сервиса.

### 5. Обновлён граф знаний
- **Команда:** `graphify update .`
- **Результат:** Граф знаний актуализирован (940 узлов, 2440 ребра, 73 сообщества).

## Выполненные изменения фронтенда (xo-os-web)

### Header.js
- Добавлено состояние пользователя (`user`), статус синхронизации (`syncStatus`), время последней проверки (`lastCheck`) и онлайн/офлайн (`online`).
- При монтировании компонента выполняется запрос к `/api/auth/me` для получения данных текущего пользователя (имя, email).
- Запущен периодический опрос (каждые 30 секунд) эндпоинтов `/api/google/status` и `/api/health` для обновления статуса синхронизации и соединения.
- В шапке теперь отображается:
  - Имя пользователя вместо статичного "Пользователь".
  - Динамический статус синхронизации ("Синхронизировано"/"Не синхронизировано").
  - Динамический индикатор онлайн/офлайн.
  - Кнопка выхода, которая отправляет POST запрос на `/api/auth/logout` и очищает состояние пользователя.

### Sidebar.js
- Добавлено состояние статуса синхронизации (`syncStatus`), времени последней синхронизации (`lastSync`), онлайн/офлайн (`online`) и версии (`version`).
- При монтировании и каждые 30 секунд выполняются запросы к:
  - `/api/google/status` – статус синхронизации с Google Calendar.
  - `/api/health` – проверка доступности бэкенда (онлайн/офлайн).
  - `/api/stats` – попытка получить статистику (в текущей реализации используется как триггер для обновления времени).
- В сайдбаре теперь отображается:
  - Динамический статус синхронизации Google Calendar.
  - Динамическое время последней синхронизации.
  - Динамический индикатор онлайн/офлайн.
  - Текущая версия (пока хардкожена, но может быть получена от бэкенда при наличии соответствующего эндпоинта).

## Как проверять

1. **Регистрация:**
   - Откройте форму регистрации, заполните поля и отправьте.
   - Ожидайте ответ 200 OK с сообщением о отправленном письме и данными пользователя.
   - На почту должно прийти письмо со ссылкой подтверждения.

2. **Подтверждение email:**
   - Перейдите по ссылке из письма (она будет вида `http://127.0.0.1:8000/verify-email?token=...`).
   - Ожидайте ответ 200 OK и автоматический вход в систему (установка cookie сессии).
   - После этого вы должны быть авторизованы.

3. **Вход в систему:**
   - Откройте страницу логина, введите email и пароль.
   - Ожидайте успешный вход (ответ 200 OK с данными пользователя и установкой cookie сессии).
   - При повторном обращении к `/api/auth/status` должно показывать `authenticated: true`.

4. **Выход из системы:**
   - Нажмите кнопку "Выход" в шапке интерфейса.
   - Ожидайте очистку состояния пользователя и перенаправление на неавторизованный вид.

5. **Проверка динамических элементов:**
   - После успешного входа в шапке должно отображаться ваше имя.
   - Статус синхронизации и соединение должны обновляться при изменении состояния бэкенда (например, при отключении/подключении интернета или при изменении статуса Google Calendar).
   - В сайдбаре аналогично должны отображаться актуальные данные.

## Примечания

- Для корректной работы убедитесь, что файл `.env` содержит верные учетные данные SMTP (например, для Gmail ne обходимо использовать пароль приложения) и правильный `XO_OS_FRONTEND_URL` (по умолчанию `http://127.0.0.1:8000`).
- Если вы используете VPN или прокси, убедитесь, что они не блокируют соединение с smtp.gmail.com:587.
- После изменения фронтенда может потребоваться перезапуск dev‑сервера (`npm start` или аналогично) для применения изменений.
- Граф знаний обновлён; для дальнейшего исследования кода можно использовать команды `/graphify query`, `/graphify explain` и `/graphify path`.

Система теперь должна полностью поддерживать поток регистрации → подтверждение email → вход в систему, а также отображать актуальную информацию о пользователе и состоянии соединения в интерфейсе.
