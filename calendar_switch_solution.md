# Инженерное решение по переключению Google Calendar в XO_OS

## 1. Рекомендуемая архитектура

Для реализации безопасного переключения между Google Calendar календарями с переносом только событий уроков XO_OS предлагается следующая архитектура:

- **Фоновая задача переключения**: Добавить новый метод `switch_calendar_for_user` в `GoogleCalendarSyncService`, который будет обрабатывать перенос событий из source-календаря в target-календарь.
- **Механизм блокировки**: Добавить таблицу `calendar_switch_locks` для сериализации операций переключения на пользователя и предотвращения гонок при быстрых переключениях.
- **Атомарная обработка уроков**: Обрабатывать каждый урок в отдельной database транзакции с блокировкой соответствующих записей для обеспечения согласованности при частичных сбоях.
- **Использование существующих функций**: Переиспользовать существующие методы аутентификации и работы с Google Calendar API, но добавить специальную логику для перемещения событий.

## 2. Необходимые изменения

### 2.1. Добавить новую таблицу для блокировки переключений
**Файл**: `app/database/models.py`
**Изменения**: Добавить модель `CalendarSwitchLock`

```python
class CalendarSwitchLock(Base):
    __tablename__ = "calendar_switch_locks"

    id: Mapped[int] = mapped_column(
        Integer,
        primary_key=True,
        index=True,
    )
    user_id: Mapped[int] = mapped_column(
        Integer,
        ForeignKey("users.id"),
        nullable=False,
        unique=True,
        index=True,
    )
    locked_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        nullable=False,
        default=datetime.now(timezone.utc),
    )
    
    user: Mapped["User"] = relationship()
```

- Если существует соединение со старым календарем и оно отличается от нового - запустить задачу переключения
- Иначе - запустить задачу начальной синхронизации

## 3. Пошаговый алгоритм переключения календаря

### 3.1. Общий flow
1. Пользователь выбирает новый календарь через веб-интерфейс
2. Маршрут `/calendar/select` сохраняет старый календарь и обновляет `selected_calendar_id`
3. Если существует соединение со старым календарем:
   - Пытается взять блокировку для пользователя в таблице `calendar_switch_locks`
   - Если блокировка получена - запускает фоновую задачу переключения
   - Иначе - логирует предупреждение и пропускает переключение (будет выполнено при следующем выборе календаря)
4. Если соединения со старым календарем нет - запускает начальную синхронизацию для нового календаря

### 3.2. Фоновая задача переключения (switch_calendar_for_user)
1. Получить соединения пользователя для source и target календарей
2. Если любое из соединений отсутствует - завершить с ошибкой
3. Получить список уроков, связанных с source-соединением (через join с GoogleCalendarEvent)
4. Для каждого урока из списка:
   a. Начать database транзакцию с блокировкой записи урока и соответствующей GoogleCalendarEvent (если существует)
   b. Получить текущее состояние урока и GoogleCalendarEvent
   c. В зависимости от состояния:
      - Если урок имеет google_event_id и есть соответствующая GoogleCalendarEvent для source:
        * Попытаться получить событие из source календаря по google_event_id
        * Если событие найдено:
          - Создать такое же событие в target календаре
          - Если creation успешна:
            * Попытаться удалить событие из source календаря (игнорировать ошибку "не найдено")
            * Обновить уроку google_event_id на новый ID
            * Обновить GoogleCalendarRecord: connection_id на target, google_event_id на новый ID, обновить поля события
            * Закоммитить транзакцию
          - Если creation неудачна - откатить транзакцию и перейти к следующему уроку
        * Если evento не найдено в source:
          - Считать запись GoogleCalendarEvent устаревшей
          - Очистить google_event_id урока
          - Удалить устаревшую GoogleCalendarEvent запись
          - Перейти к обработке как урока без события (см. ниже)
      - Если урок не имеет google_event_id или нет соответствующей GoogleCalendarEvent:
        * Создать новое событие в target календаре из данных урока
        * Если creation успешна:
          - Сохранить google_event_id урока
          - Создать новую GoogleCalendarEvent запись привязанную к target соединению
          - Закоммитить транзакцию
        * Если creation неудачна - откатить транзакцию и перейти к следующему уроку
5. Освободить блокировку (удалить запись из calendar_switch_locks)

### 3.3. Обработание ошибок и восстановление
- Каждый урок обрабатывается в独立的事务 - неудача с одним уроком не влияет на другие
- Фоновая задача может быть безопасно перезапущена - уже обработанные уроки будут пропущены (так как они больше не привязаны к source соединению)
- Блокировка автоматически освобождается при завершении задачи (успешном или с ошибкой)

| **Быстрое переключение A→B→C** | Пользователь не дожидался завершения A→B | Блокировка предотвратит одновременное выполнение, A→B завершится, затем B→C | Корректно, при условии что A→B завершилось перед началом B→C |
| **Недостаточные права API** | Ошибка при попытке чтения/записи в календарь | Все уроки в текущей транзакции не будут обработаны, блокировка будет освобождена | При следующем запуске повторится попытка |
| **Ошибка commit после обработки нескольких уроков** | Некоторые уроки успешно обработаны и закоммичены, другие нет | Успешно обработанные уроки останутся в target, неудачные останутся в source | Частичный успех, при повторном запуске будут обработаны оставшиеся уроки |

## 5. Минимальная матрица тестов

| Тест | Начальное состояние | Имитация сбоя | Ожидаемый итог |
|------|---------------------|---------------|----------------|
| Успешный перенос A→B | Уроки с событиями в A, нет в B | Нет | Все события уроков перенесены из A в B, ссылки обновлены, связи сохранены |
| Обратный перенос B→A | После A→B: события уроков в B | Нет | События возвращаются в A, ссылки обновлены обратно |
| Повторное выполнение задачи | После успешного A→B | Нет | Уроки не обработаны (вынуждены пропустить, так как уже привязаны к B) |
| API timeout после возможного успешного переноса | Event создан в B, попытка удаления из A не выполшена | Timeout при удалении из A | При повторном запуске: событие найдено в A -> попытка создания в B (может создать дубликат) -> удаление из A |
| Сбой БД после успешного API вызова | Event успешно создан в B и удален из A | Ошибка при обновлении уроков и GCE | При повторном запуске: событие НЕ найдено в A -> создание нового в B (дубликат) |
| Изменившийся event ID | Google вернул новый ID при создании в B | Нет | ID урока и GCE обновлен на новый ID |
| Конфликт нового ID с другим уроком | При создании в B получен ID, который уже используется другим уроком в B | Нет | Требует ручного вмешательства (вне текущего решения) |
| Событие отсутствует в обоих календарях | Урок имеет google_eventid, но события нет ни в A, ни в B | Нет | При переключении A→B: создаст новое событие в B |
| Потерянная запись GCE | Урок имеет google_eventid, но нет GCE записи для соединения A | Нет | При переключении A→B: создаст новое событие в B (так как не найдено GCE для A) |
| Личные события в source и target | Личные события в обоих календарях + eventi уроков | Нет | Личные события остаются без изменений, только eventi уроков переносятся |
| Быстрое переключение A→B→C | Выполнено A→B, затем сразу B→C без ожидания | Нет | Сначала перенос A→B, затем B→C |
| Два конкурентных переключения | Попытка запустить A→B и B→A одновременно | Нет | Блокировка не позволит второму запуску начаться пока не завершится первый |
| Недостаточные права и временные ошибки API | Ошибка 403/429 при вызове API | Нет | Уроки не обработаны в текущей итерации, блокировка освобождена, повторная попытка позже |
| Ошибка commit после обработки нескольких уроков | Ошибка при коммите после обработки N уроков | Нет | Первые N уроков в целевом календаре, остальные в источнике |

## 6. Ограничения и оставшиеся риски

1. **Риск создания дубликатов**: При определенных сценариях сбоя (успешное создание в target + падение до commit) может происходить создание дубликат событий при повторном запуке переключения.

2. **Ограничение на обработку коллизий event ID**: Текущее решение не обрабатывает случай, когда Google Calendar возвращает event ID, который уже занят другим событием в целевом календаре.

3. **Зависимость от блокировок на уровне базы данных**: Решение использует database-level блокировки (FOR UPDATE) для обеспечения согласованности при обработке отдельных уроков.

4. **Время выполнения при большом количестве уроков**: Обработка уроков по одному в отдельных транзакциях может занимать значительное время при большом количестве уроков.

5. **Отсутствие проверки дубликатов в целевом календаре**: Перед созданием события в целевом календаре не выполняется проверка на существование аналогичного события (по времени и содержанию).

6. **Требование к миграции базы данных**: Необходимо добавить новую таблицу `calendar_switch_locks`, что требует миграции схемы базы данных.
