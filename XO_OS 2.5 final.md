## 2. Финальные формулы

### 2.1. Focus

**Определение:** доля завершённых фокус-сессий, которые являются продуктивными.

- Единица расчёта — фокус-сессия со статусом `completed`.
- В `completed_sessions` включаются только сессии со статусом `completed`.
- Сессии `active` и `paused` не включаются до завершения.
- Продуктивная сессия: `productive_duration >= 25 * 60`, где `productive_duration` — продуктивное время сессии без пауз.
- AI-верификация на Focus не влияет.

```
completed_sessions = count(sessions where status = 'completed')

productive_sessions = count(
    sessions where status = 'completed'
    and productive_duration >= 25 * 60
)

Focus = null, если completed_sessions = 0
Focus = productive_sessions / completed_sessions * 100,
        если completed_sessions > 0
```

Окно расчёта: последние 7 календарных дней, включая текущий день.

### 2.2. Productivity

**Определение:** взвешенная доля выполненных задач в окне.

```
Productivity = Σ(estimated_value × completion_state) / Σ(estimated_value) × 100
```

**Состав знаменателя.** В знаменатель входят все обязательства окна **кроме** `excused` и `auto_exempt`.

`completion_state` по статусу обязательства:

| Статус обязательства | `completion_state` | Входит в знаменатель |
|---|---|---|
| `done` | 1.0 | да |
| `partial` | 0.5 | да |
| `active` | 0.0 | да, если срок ещё не истёк и обязательство входит в окно |
| `missed` | 0.0 | да |
| `excused` | — | нет |
| `auto_exempt` | — | нет |

`partial` — обязательство выполнено частично по явной процедуре фиксации частичного результата. Для учебного события этот статус не устанавливается автоматически только на основании покрытия менее 15 минут. Если частичное выполнение не зафиксировано отдельно, обязательство остаётся `active` до истечения срока, после чего переходит в `missed`.

Правила `done`:

- **Учебные события:** `productive_intersection >= 15 * 60` или `user_marked_as_done = true`.
- **Личные задачи:** только `productive_intersection >= 15 * 60`. `user_marked_as_done` на личные задачи не влияет.

`estimated_value`:

- **Учебные события:** из `Lesson.estimated_value`. При `null` — по типу: лекция 3, практика 5, лабораторная 4.
- **Личные задачи:** по умолчанию 3, пользователь может изменить.

`load_factor` для `estimated_value` не используется.

AI-верификация в формулу не входит.

**Нулевой знаменатель:** если `Σ estimated_value = 0`, `Productivity = null` с пояснением «Нет значимых обязательств».

Окно расчёта: последние 7 календарных дней, включая текущий день.

### 2.3. Energy

**Определение:** условный игровой индикатор нагрузки и восстановления. Не является медицинским показателем.

Восстановление:

```
E(t) = 100 − (100 − E₀) × exp(−decay × t)
```

Обозначения и единицы:

- `t` — время с момента `last_energy_update`, в **часах**.
- `decay = 0.15` — коэффициент **в час** (1/час).
- `consumption_rate = 0.5` — единиц энергии на продуктивную **минуту**.
- `energy_max = 100`.
- хранение в БД — `Float`, округление только в интерфейсе.

Параметры считаются начальными и допускают калибровку по факту использования без пересмотра спецификации.

Расход при завершении сессии:

1. `t_hours = (now − last_energy_update) / 3600`
2. `base = E(t_hours)`
3. `consumption = productive_minutes × consumption_rate × load_factor × fatigue_modifier`
4. `energy = max(0, base − consumption)`
5. `last_energy_update = now`

Чтение API не изменяет `last_energy_update` и не сохраняет восстановленное значение.

Таблица `load_factor`:

| Тип нагрузки | load_factor |
|---|---:|
| Чтение или просмотр | 0.7 |
| Письмо или конспект | 1.0 |
| Решение задач | 1.2 |
| Программирование | 1.3 |
| Экзамен или тест | 1.5 |
| Неизвестный тип | 1.0 |

Для учебных событий `load_factor` определяется через `Lesson.lesson_type`. Для личных задач — задаётся пользователем, по умолчанию 1.0.

Усталость:

```
fatigue_modifier = 1.0 + (last_fatigue_assessment − 50) / 200
```

- `fatigue_modifier` вычисляется по формуле выше и ограничивается диапазоном **0.75–1.25 включительно**.
- TTL 6 часов. Старше — `fatigue_modifier = 1.0`.
- Запрашивается только после сессии с продуктивным временем > 30 минут.

Начальные значения при миграции:

- `energy = 100.0`
- `last_energy_update = момент миграции`
- `last_fatigue_assessment = NULL`

UI обязательно показывает: «Условный игровой индикатор. Не является медицинским показателем».

### 2.4. Discipline

**Определение:** доля выполненных обязательств среди обязательств, входящих в расчёт.

Статусы **обязательства** (`status`):

- `active` — решение ещё не принято, срок не истёк.
- `partial` — явно зафиксированное частичное выполнение. Устанавливается **только пользователем** через явную процедуру фиксации частичного результата (например, отметка в интерфейсе или вызов API). Не устанавливается автоматически по продолжительности сессии, покрытию события или любому другому условию.
- `done` — выполнено.
- `missed` — пропущено.
- `excused` — причина признана уважительной.
- `auto_exempt` — обязательство исключено из расчёта.

**Статус причины** (`reason_status`) — отдельное поле:

- `none`, `no_response`, `pending_reason`, `excused`, `rejected`.

`rejected` — значение `reason_status`, не статус обязательства.

```
Обязательства_к_учёту = done + missed

Discipline = null, если Обязательства_к_учёту = 0
Discipline = done / Обязательства_к_учёту × 100,
             если Обязательства_к_учёту > 0
```

Правила учёта:

- `excused` и `auto_exempt` исключаются из знаменателя полностью.
- `active` (в том числе с `reason_status = pending_reason` или `no_response`) **не входит ни в числитель, ни в знаменатель**, пока срок не истёк.
- `partial` **не входит ни в числитель, ни в знаменатель** формулы Discipline. Причина: Discipline измеряет соблюдение обязательств (выполнено / не выполнено), а частичное выполнение не является ни полным выполнением, ни пропуском. Частичный результат учитывается в Productivity, но не в Discipline.
- После истечения `event.end_time + 24 часа` неразрешённое обязательство переходит в `missed` и входит в знаменатель — даже если причина ещё ожидает рассмотрения.
- Статус `partial` после истечения срока **автоматически не меняется** (сохраняется как явное частичное выполнение).
- Доля `pending_reason` **в скользящем окне 30 календарных дней** отдельно контролируется: если превышает 30 %, `Discipline = null` с пояснением «Ожидает разбора».

Автоматических санкций за частоту причин нет.

**Переход в `missed`** — после `event.end_time + 24 часа`, если обязательство не выполнено и причина не подтверждена.

**Позднее выполнение** (после закрытия в `missed`) сохраняется в истории, но **не меняет терминальный статус** на `done`.

## 3. Правило 15 минут

Правило покрытия события и метрика Focus — разные механизмы с разными порогами:

- 15 минут — покрытие события.
- 25 минут — продуктивная сессия для Focus.

```
intersection_start = max(S.started_at, E.start_time)
intersection_end = min(S.ended_at, E.end_time)
intersection_duration = max(0, intersection_end − intersection_start)

paused_within = длина объединения интервалов пауз внутри пересечения
productive_intersection = intersection_duration − paused_within

covered = productive_intersection >= 15 * 60
```

Перекрывающиеся паузы считаются как объединение интервалов.

Паузы хранятся в `focus_session_pauses` (`id`, `session_id`, `started_at`, `ended_at`).

Одна сессия привязывается максимум к одному событию через `FocusSession.intended_lesson_occurrence_id`. Поле задаётся только при старте в `FocusService.start_focus_session`. Попытка смены после старта возвращает 400 Bad Request (проверка в сервисном слое).

Внеплановая сессия не засчитывается ни одному обязательству.

Для исторических сессий с `pauses_complete = false`: `paused_within = 0` как технический fallback. Результат считается **приблизительным** и не должен представляться в истории как точное покрытие.

Термины, которые нельзя смешивать:

- продолжительность всей сессии,
- продуктивная продолжительность,
- пересечение с событием,
- покрытие события,
- порог продуктивной сессии Focus.

## 4. AI-верификация

### 4.1. Начисление XP

Начисление XP атомарно:

- транзакция БД,
- блокировка строки `FocusSession` через `SELECT ... FOR UPDATE`,
- проверка `verification_status = 'approved'` — условие **начисления**,
- проверка `xp_awarded_at IS NULL` — защита от повторного начисления,
- повторное начисление запрещено.

В `process_ai_verification_result` обработка начинается с сессии в статусе `pending`. Это условие **обработки**, а не начисления. Начисление XP происходит только при переходе в `approved`.

`FocusSession.xp_awarded_at` — nullable DateTime.

### 4.2. Попытки

- `attempt_number` монотонно растёт в пределах `focus_session_id`, включая `error`.
- `user_attempt = true` только при первичной пользовательской отправке и одной корректировке после `rejected`.
- `error` не расходует пользовательскую попытку.
- Резервирование попытки — в той же транзакции с блокировкой строки сессии. Проверка: `COUNT(*) WHERE user_attempt = true AND focus_session_id = X < 2`.
- Уникальный ключ `(focus_session_id, attempt_number)`.
- Не более двух автоматических повторов `error` с экспоненциальной задержкой.
- Одна пользовательская корректировка после `rejected` — в течение **24 часов**.

### 4.3. Различие error и rejected

- `error` — техническая невозможность: недоступен сервис, таймаут, 5xx, невалидный ответ, отсутствие обязательных полей.
- `rejected` — проверка завершилась корректно, AI вернул отрицательный результат, включая «не могу сопоставить с целью».

### 4.4. Снимки

`goal_text_snapshot` и `evidence_snapshot` неизменяемы после создания.

`what_changed` хранит diff между попытками.

Таблица `ai_verification_attempts`: `id`, `focus_session_id`, `attempt_number`, `user_attempt`, `goal_text_snapshot`, `evidence_snapshot`, `ai_result`, `ai_reason`, `ai_missing`, `ai_score`, `user_correction_applied`, `what_changed`, `created_at`.

## 6. Жизненный цикл обязательства

**Статусы обязательства (`status`):** `active`, `partial`, `done`, `missed`, `excused`, `auto_exempt`.
**Статусы причины (`reason_status`):** `none`, `no_response`, `pending_reason`, `excused`, `rejected`.

**До истечения `event.end_time + 24 часа`:**

```
создано → active
active → done (покрытие или ручная отметка для учебного события)
active → excused (причина подтверждена до закрытия)
active → partial (пользователь явно зафиксировал частичное выполнение)
active + reason_status = pending_reason (причина введена, ожидает рассмотрения)
active + reason_status = no_response (вопрос показан, ответа нет)
no_response → pending_reason (пользователь позднее ввёл причину, срок не истёк)
partial → done (если частично выполненное обязательство позже выполнено полностью)
```

**По истечении `event.end_time + 24 часа`:**

```
active (без выполнения и без подтверждённой причины) → missed
  reason_status = none           → status = missed, reason_status = none
  reason_status = no_response    → status = missed, reason_status = no_response
  reason_status = pending_reason → status = missed, reason_status = pending_reason
                                   (обязательство закрыто, но причина ещё может быть рассмотрена)

pending_reason (после закрытия) → причина отклонена:
  reason_status = rejected, status остаётся missed

pending_reason (после закрытия) → причина подтверждена:
  status = excused (пересмотр)

partial (независимо от истечения срока) → статус остаётся partial
  (явное частичное выполнение не меняется автоматически)
```

**Поздний ответ после закрытия:** сохраняется в аудите, но не открывает обязательство повторно. Если причина подтверждена после закрытия — статус может быть пересмотрен на `excused` через отдельную процедуру пересмотра (не автоматически).

Терминальные статусы (`done`, `excused`, `auto_exempt`) не имеют исходящих переходов. `missed` — терминальный для обычного потока; пересмотр возможен только через явную процедуру, не через автоматический переход.

**Автоподтверждение причины.** Автоподтверждение выполняется через 24 часа после подачи причины, независимо от того, истёк ли срок обязательства.

- Если на момент автоподтверждения обязательство ещё `active` — статус устанавливается в `excused`, и последующий переход в `missed` не выполняется.
- Если обязательство уже в `missed` — автоподтверждение **не меняет** статус автоматически. Для перевода `missed → excused` требуется отдельная процедура пересмотра.
- Если обязательство в статусе `partial` — автоподтверждение **не меняет** статус (остаётся `partial`).
- Правило действует независимо от того, истёк ли срок события.

## 7. Обратная связь

`no_response` — вопрос показан, ответа нет. Если срок истёк — обязательство закрывается в `missed`.

`pending_reason` — причина введена, ожидает рассмотрения.

Enum `reason_status`: `none`, `no_response`, `pending_reason`, `excused`, `rejected`.

Вопрос показывается только в двух случаях:

1. Обязательство не выполнено: событие не покрыто и причины нет.
2. Прервана серия: `current_streak` снизился.

Вопрос не показывается только потому, что в текущем дне нет активности.

Формат ответа — закрытый список причин и поле «Другое».

Отсутствие ответа фиксируется. Автоматических санкций за частоту причин нет.

**Автоподтверждение причин** описано в разделе 6. Правило: через 24 часа после подачи причины. Поведение при уже закрытом обязательстве — без автоматического пересмотра. Поведение при `partial` — статус не меняется.

## 8. Изменения модели данных

## 10. Что изменилось между версиями 2.1 и 2.5

| Область | В ранней версии | В 2.5 | Причина |
|---|---|---|---|
| Focus | Все сессии, включая незавершённые | Только `completed`, порог 25 минут, окно 7 дней | Уточнение семантики |
| Productivity | Доля затраченного времени | Взвешенная сумма с явным составом знаменателя и `null` при нуле | Учёт значимости задач |
| Energy | Нет детализированной модели | Асимптотическое восстановление, `load_factor`, усталость, единицы времени | Точность модели |
| Discipline | Только `done` / `missed` | Разделены статусы обязательства и причины, добавлен `partial`, порог 30 %, окно 30 дней для доли | Чёткая семантика |
| Покрытие события | 15 минут для Focus и события | 15 — покрытие, 25 — Focus | Разведение концепций |
| Паузы | Суммарное время | Таблица `focus_session_pauses`, флаг `pauses_complete`, пометка «приблизительно» | Точность пересечения |
| AI-верификация | Нет атомарности | `SELECT ... FOR UPDATE`, `xp_awarded_at`, уникальная попытка, лимит ретраев | Защита от гонок |
| История | Базовые поля | Расширенная схема с разделением привязки и покрытия | Отслеживание связи и верификации |
| Модель данных | Без энергетики, привязок, попыток | Поля и таблицы раздела 8 | Синхронизация с формулами |
| Обратная связь | Без разделения | `no_response` и `pending_reason` разделены, автоподтверждение через 24 часа | Чёткое влияние на Discipline |
| Порядок этапов | Другой порядок | Семантика → история → Energy → AI → обязательства → метрики | Логическая зависимость |

## 11. Продуктовые решения

Все перечисленные ниже решения приняты как рабочие для версии 2.5. Они могут быть пересмотрены при появлении данных из реального использования, но не блокируют реализацию.

| № | Решение | Значение |
|---|---|---|
| 1 | Окно метрик | 7 календарных дней, включая текущий день |
| 2 | Параметры Energy | `decay = 0.15`, `consumption_rate = 0.5`, `energy_max = 100` — начальные, калибруются |
| 3 | TTL усталости | 6 часов |
| 4 | Порог `pending_reason` | 30 % |
| 5 | Окно для доли `pending_reason` | Скользящие 30 календарных дней |
| 6 | Порог продуктивной сессии Focus | 25 минут |
| 7 | Подтверждение уважительных причин | Автоподтверждение через 24 часа |
| 8 | Лимит `error`-ретраев | Не более двух, с экспоненциальной задержкой |
| 9 | Срок корректировки после `rejected` | 24 часа |
| 10 | Позднее выполнение | Сохраняется в истории, не меняет терминальный статус |
| 11 | Нулевой знаменатель Productivity | `null` с пояснением «Нет значимых обязательств» |
| 12 | Хранение доказательств | `evidence_count` и `evidence_types`, без ссылок на файлы |
