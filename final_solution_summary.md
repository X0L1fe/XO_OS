# Итоговое инженерное решение по переключению Google Calendar

## 1. Рекомендуемая архитектура
Добавить фоновую задачу переключения календаря с механизмом блокировок и транзакционной обработкой уроков по одному для обеспечения согласованности при частичных сбоях.

## 2. Необходимые изменения
1. Добавить таблицу `calendar_switch_locks` в `app/database/models.py` для сериализации операций переключения
2. Расширить `GoogleCalendarSyncService` в `app/google_calendar/service.py` методом `switch_calendar_for_user()`
3. Обновить маршрут `/calendar/select` в `app/google_calendar/routes.py` для выбора между переключением и начальной синхронизацией

## 3. Пошаговый алгоритм
1. При выборе нового календаря сохраняется старый `selected_calendar_id`
2. Если существует соединение со старым календарем - пытаемся взять блокировку для пользователя
3. При успешной блокировке запускается фоновая задача переключения:
   - Для каждого урока, связанного со старым календарем, выполняется отдельная транзакция:
     * Если урок имеет событие в источнике - копируем его в целевой календарь, удаляем из источника, обновляем ссылки
     * Если урок не имеет события в источнике - создаем новое событие в целевом календаре
   - Транзакция обеспечивает атомарность обработки каждого урока
4. Блокировка освобождается после завершения обработки всех уроков

## 4. Таблица восстановления после сбоев
Основные сценарии сбоев обрабатываются через повторную попытку обработки уроков:
- Успешное API событие + сбой БД → при повторном запуске событие не найдено в источнике → создание нового в целевом календаре
- Событие создано в целевом календаре + сбой при удалении из источника → при повторном запуске попытка создания в целевом (возможный дубликат) + удаление из источника
- Потерянная запись GoogleCalendarEvent → обрабатывается как урок без события
- Конкурентные переключения предотвращаются блокировкой на пользователя

## 5. Минимальная матрица тестов
Покрывает успешный перенос, обратный перенор, повторное выполнение, API таймауты, сбои БД, изменяющиеся event ID, конфликты ID, отсутствие событий, потерянные записи GCE, личные события, быстрое переключение, конкурентные операции, ошибки API и ошибки коммита.

## 6. Ограничения и оставшиеся риски
- Риск создания дубликатов при определенных сценариях сбоя
- Не обрабатывается коллизия event ID при создании в целевом календаре
- Возможны дубликаты при повторном запуске после частичного успеха
- Требуется миграция для добавления таблицы блокировок
- Обработка уроков по одной может быть медленной при большом количестве уроков
